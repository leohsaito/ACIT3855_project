# Soccer Stadium Storage Service

The storage service receives events from the receiver and persists them in MySQL using SQLAlchemy. It also provides GET endpoints used by the processing service to retrieve only events recorded after a given timestamp.

The storage service is **internal to Docker** and is not exposed to the host in the final Lab 7 architecture.

## Architecture

```text
Receiver
   |
   | POST
   v
Storage :8090
   |
   | SQLAlchemy / PyMySQL
   v
MySQL :3306

Processing
   |
   | GET ?after=<recorded_timestamp>
   v
Storage :8090
```

Docker Compose service names are used for internal communication.

## Database Configuration

The database connection is read from `DATABASE_URL`.

Local default:

```text
mysql+pymysql://soccer_user:soccer_password@127.0.0.1:3306/soccer_events
```

Docker Compose value:

```text
mysql+pymysql://soccer_user:soccer_password@db:3306/soccer_events
```

Inside the storage container, MySQL is reached using the Docker service name `db`.

## Database Tables

The service stores two event types:

- `attendance`
- `ticket_sale`

Important fields include:

```text
id
trace_id
event data
timestamp
recorded_timestamp
```

### `timestamp` vs `recorded_timestamp`

`timestamp` is when the event happened and comes from the event payload/JMeter.

`recorded_timestamp` is generated by the storage service when the database record is created.

The processing service filters on **`recorded_timestamp`**, not the event timestamp.

The timestamp columns use microsecond precision (`TIMESTAMP(fsp=6)`) so that high-volume JMeter events can be distinguished reliably.

## API Routes

| Method | Route | Purpose |
|---|---|---|
| POST | `/stadiums/attendance` | Store attendance event |
| GET | `/stadiums/attendance?after=<datetime>` | Retrieve attendance events recorded after a timestamp |
| POST | `/stadiums/ticket-sales` | Store ticket-sale event |
| GET | `/stadiums/ticket-sales?after=<datetime>` | Retrieve ticket-sale events recorded after a timestamp |
| GET | `/status` | Health check; can include database record counts |
| POST | `/reset` | Optional Lab 4 debugging route to drop/recreate tables, if implemented |

When `after` is omitted, the GET endpoints can return all records. When no matching records exist, they return an empty JSON array.

## Run with Docker Compose

From the project root:

```powershell
docker compose up -d --build
```

Check storage health:

```powershell
docker compose ps
```

In the final setup, storage should **not** show a host mapping such as `0.0.0.0:8090->8090`. That is intentional.

## Accessing Storage from Docker

Because port `8090` is internal, this will normally **not** work from the Windows browser:

```text
http://127.0.0.1:8090/ui/
```

Test storage from inside the container instead:

```powershell
docker compose exec storage curl -s http://127.0.0.1:8090/status
```

Other containers use:

```text
http://storage:8090
```

## Create and Drop Tables

Run the scripts inside the storage container so they use the Docker database URL:

```powershell
docker compose exec storage python create_tables.py
```

```powershell
docker compose exec storage python drop_tables.py
```

Do not run these locally unless MySQL is also exposed to the host and the local `DATABASE_URL` is correct.

## Optional `/status` and `/reset`

A useful `/status` response is:

```json
{
  "status": "running",
  "attendance_count": 31,
  "ticket_sale_count": 25
}
```

This is stronger than a simple `running` response because it also proves storage can query MySQL.

If `/reset` is implemented:

```powershell
docker compose exec storage curl -i `
  -X POST http://127.0.0.1:8090/reset
```

**Important:** resetting MySQL does not automatically reset the processing service's persistent statistics. These are separate microservices and should remain decoupled.

## Project Defense Guide

### What to Demonstrate

1. Show that storage is healthy but has no host port with `docker compose ps`.
2. Query `/status` from inside the storage container.
3. Show MySQL row counts.
4. Run JMeter against the receiver and show that the row counts increase.
5. Explain the GET endpoints with the `after` parameter.
6. Show that a stored `trace_id` matches the receiver/storage logs.

### Be Ready to Explain

**Why is storage not exposed to the host?**  
It is an internal microservice. Only receiver and processing need host-facing API ports.

**Why do the GET endpoints use `recorded_timestamp`?**  
Processing needs to know which records are new since its last poll. Event timestamps describe when an event happened, not necessarily when storage received it.

**Why use microsecond precision?**  
JMeter can generate many requests in the same second. Greater precision reduces the risk of events sharing the same cursor timestamp and being missed during incremental polling.

**Why use `after` instead of retrieving the entire table every five seconds?**  
Incremental retrieval is much more efficient and scales better as the database grows.

**Why does `create_all()` not update an existing schema?**  
SQLAlchemy `create_all()` creates missing tables but does not perform schema migrations. During development, changed table definitions may require dropping/recreating tables or using a migration tool.

**Why use environment configuration for `DATABASE_URL`?**  
The database host differs locally and inside Docker. External configuration keeps deployment details outside the source code.
